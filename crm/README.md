# CRM подписного SMM-сервиса

Интерфейс `Клиенты.dc.html` + бэкенд на Google Apps Script (`Code.gs`).

`Code.gs` состоит из двух частей в одном файле:

1. **Учёт оплат** — рабочий код: `onEdit`, `checkPayments`, `addDropdown`,
   `createTrigger`, `shiftMonths`, `paintStatus`, `startOfDay`,
   `sendTelegram` и константы. Не менялся.
2. **CRM** — `doGet` / `doPost` для интерфейса, GitHub, RouterAI и
   `onFormSubmit`. Ничего из первой части не переопределяет.

Оплатами распоряжается только первая часть: статус ставится дропдауном в
колонке «Статус», дату двигает `onEdit`, напоминания шлёт `checkPayments`.
В CRM нет ни `action=pay`, ни `action=unpay` — кнопка в карточке открывает
нужную строку листа на ячейке статуса.

**Токены Telegram в этом файле — заглушки:** репозиторий публичный.
Рабочие значения `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` живут в проекте
Apps Script; обновляя файл из репозитория, не затрите их.

```
Google Форма ──onFormSubmit──► лист «Клиенты» ──► Telegram-уведомление
                                    ▲  │
  браузер ── fetch ──► Web App ──────┘  ├──► GitHub Contents API → clients/{id}.json → workflow_dispatch
   (Клиенты.dc.html)   (Code.gs)        └──► RouterAI (google/gemini-3.1-pro-preview)
```

Все секреты — GitHub PAT, ключ RouterAI, токен Telegram — лежат в Script
Properties. Браузер их не получает и не отправляет: он знает только адрес
Web App и токен доступа к нему.

## Что делает бэкенд

| Запрос | Что происходит |
| --- | --- |
| `GET ?action=clients` | все клиенты из листа «Клиенты» |
| `GET ?action=client&id=X` | один клиент |
| `GET ?action=briefs` | необработанные ответы формы из листа «Брифы» |
| `GET ?action=log` | записи из листа «Лог», свежие сверху |
| `GET ?action=settings` | какие свойства скрипта заданы (да/нет, без значений) |
| `GET ?action=ping` | проверка таблицы, GitHub, RouterAI и Telegram |
| `POST action=save` | сохраняет карточку клиента (переданные поля, остальные не трогает) |
| `POST action=new` | создаёт клиента вручную или из брифа, выдаёт `client_id` |
| `POST action=push` | GET sha → PUT `clients/{id}.json` → `workflow_dispatch` |
| `POST action=analyze_style` | пять текстов клиента → `style_prompt` |
| `POST action=build_plan` | бриф → рубрики с промптами |
| `POST action=gen_examples` | пример поста для каждой рубрики с учётом `style_prompt` |
| `POST action=apply_edits` | правки клиента → обновлённые промпты и примеры |
| `POST action=brief_dismiss` | помечает бриф отложенным |

Ответ всегда JSON: `{"ok": true, ...}` либо `{"ok": false, "error": "…"}`.

## Настройка

### 1. Таблица

В проекте Apps Script вашей таблицы замените содержимое файла на `Code.gs`
(и впишите реальные `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` вместо
заглушек). `appsscript.json` — манифест проекта, его видно после включения
«Показывать файл манифеста» в настройках.

Запустите функцию `setupSheets` — один раз, руками из редактора. Она
создаст листы «Брифы» и «Лог» и допишет недостающие колонки CRM **справа**
от существующих. Учёт оплат работает по фиксированным колонкам B–G, их это
не сдвигает. Во время запросов из браузера колонки не добавляются: рабочий
лист не должен меняться сам по себе — если колонок не хватает, CRM
ответит ошибкой и попросит запустить `setupSheets`.

Колонки ищутся **по названию заголовка**, поэтому CRM садится на уже
существующий лист:

| Поле CRM | Берётся из колонки |
| --- | --- |
| ФИО | «Клиент», иначе «ФИО» |
| Тариф | «Тариф» |
| Дата оплаты | «Дата оплаты» |
| Статус оплаты | «Статус» (дропдаун), иначе «Статус оплаты» |

Статусы дропдауна CRM понимает как есть: «Оплачено N мес» → оплачено,
«Ожидает оплаты» и «Отменить оплату» → ждёт оплаты, «Просрочено» →
просрочка. Если дата платежа уже прошла, а лист ещё не пересчитан
(`checkPayments` ходит раз в сутки), CRM покажет просрочку сама.

Лист **«Клиенты»**, обязательные колонки (порядок не важен, поиск идёт по
названию заголовка):

```
client_id | ФИО | Телефон | Email | Telegram | Тариф | Название бизнеса |
О бизнесе | Аудитория | Город | Соцсети | Ссылки | Тон | Слоты | Есть фото |
Рубрики (JSON) | Праздники | FAQ | Ограничения список | Ограничения текст |
Заглушка | Источник | Дата подключения | Дата оплаты | Статус оплаты |
Активен | style_prompt | Конфиг закоммичен
```

К ним `setupSheets` дописывает справа служебные колонки CRM — им не нашлось
места в основном наборе, а интерфейсу они нужны: `Ниша`, `Темы`,
`Последняя оплата`, `Предыдущая дата оплаты`, `Ответы на задания (JSON)`,
`Чек-лист (JSON)`, `Итерации`, `Фото в очереди`, `Последний пост`,
`Статус последнего поста`, `Обновлено`.

Как читаются значения:

- **Дата оплаты** — дата *следующего* платежа (по ней считаются напоминания
  и просрочка), **Последняя оплата** — когда платёж пришёл в прошлый раз.
- **Статус оплаты** — по-русски: `Оплачено`, `Ждёт оплаты`, `Просрочка`,
  `Тест без оплаты`, `Новый бриф`. Просрочка ставится автоматически, если
  дата оплаты в прошлом.
- **Предыдущая дата оплаты** — дата, которая стояла в «Дате оплаты» до
  последнего подтверждения. Заполняется автоматически, нужна для отката.
- **Слоты** — `Утро`, `День`, `Вечер` (07:00 / 11:00 / 16:00 UTC).
- **Ограничения список** и **Темы** — по одному пункту на строку внутри
  ячейки: сами пункты содержат запятые.
- **Активен** — галочка.

Лист **«Брифы»** — лист ответов Google Формы. Триггер записывает в него
`client_id` созданной карточки; в разделе «Брифы» интерфейса видны только
ответы без карточки.

Лист **«Лог»**: `client_id | Дата | Время | Рубрика | Статус | Ошибка` —
его наполняет публикующий workflow, CRM только читает.

### 2. Свойства скрипта

**Настройки проекта → Свойства скрипта.** Это единственное место, где
задаются секреты.

| Свойство | Обязательно | Значение |
| --- | --- | --- |
| `API_TOKEN` | да | длинная случайная строка; её же вводят в интерфейсе |
| `GITHUB_TOKEN` | для коммитов | PAT с правами `contents:write` и `actions:write` |
| `GITHUB_REPO` | для коммитов | `owner/repo`, например `malkhanow/vk-autopost` |
| `ROUTERAI_KEY` | для генерации | ключ RouterAI |
| `GITHUB_BRANCH` | нет | ветка, по умолчанию `main` |
| `GITHUB_WORKFLOW` | нет | файл воркфлоу для тестового прогона, по умолчанию `post.yml` |
| `CONFIG_DIR` | нет | папка конфигов, по умолчанию `clients` |
| `ROUTERAI_MODEL` | нет | по умолчанию `google/gemini-3.1-pro-preview` |
| `SPREADSHEET_ID` | нет | если скрипт не привязан к таблице |
| `TARIFF_MARKERS` | нет | переопределение разделов формы под тариф |

Telegram сюда не входит: бот и чат заданы константами в первой части
файла, CRM шлёт уведомления тем же `sendTelegram`.

Пока `API_TOKEN` не задан, проверка выключена и Web App открыт всем, у кого
есть ссылка. Задайте его сразу.

### 3. Деплой Web App

**Начать развёртывание → Веб-приложение**: запуск от вашего имени, доступ —
«Все». Скопируйте адрес, оканчивающийся на `/exec`.

Доступ «Все» нужен, чтобы страница могла обращаться к Web App без входа в
Google; от посторонних защищает `API_TOKEN`. Адрес меняется при каждом
новом развёртывании — обновляйте его в настройках интерфейса (или
разворачивайте новую версию поверх старой, тогда адрес сохранится).

### 4. Форма и триггеры

Запустите `installTriggers` — она ставит только `onFormSubmit` и чужие
триггеры не трогает.

**Порядок важен:** `createTrigger` из первой части удаляет *все* триггеры
проекта. Сначала `createTrigger` (он поставит `checkPayments` на 9:00),
потом `installTriggers`. Если запустить наоборот — триггер формы пропадёт.

Ответы формы читаются **по заголовку вопроса**, а не по номеру колонки:
вопросы можно переставлять. Соответствия заданы в `FORM_Q` в начале
`Code.gs` — если вопрос назван иначе, допишите вариант туда.

Тариф определяется по заполненному разделу: если в заголовке вопроса
название тарифа стоит ЗАГЛАВНЫМИ (`ПРО — 2 поста в день: какие слоты?`) и
в этом разделе есть ответы, берётся этот тариф; при нескольких — старший.
Строчное «про» в обычном вопросе («расскажите про бизнес») тарифом не
считается. Прямой вопрос «Какой тариф?» важнее разделов. Если ничего не
нашлось — `СТАРТ`, поправить можно в карточке.

После создания карточки уходит уведомление:
`Новый бриф: [ФИО], [тариф], [ниша]` — и следом бизнес, город, контакты и
`client_id`.

### 5. Интерфейс

Страница живёт в двух файлах:

| Файл | Что это |
| --- | --- |
| `Клиенты.dc.html` | исходник-холст Claude Design — его правим |
| `index.html` | собранная страница для GitHub Pages — не правим руками |

`.dc.html` сам по себе в браузере не работает: `{{ … }}`, `sc-for` и
`sc-if` разбирает `support.js`, рантайм холста, которого на Pages нет —
поэтому по прямой ссылке видны сами шаблоны. `build_page.py` собирает из
холста обычную страницу: разметка уезжает в `<template>`, а вместо
`support.js` встраивается `page_runtime.js` — 280 строк, которые понимают
ровно то, что использует эта разметка. Внешних зависимостей нет, весь
JavaScript внутри файла; из сети подтягиваются только шрифты Google.

После правок холста:

```
python3 crm/build_page.py
```

Адрес страницы — `https://<логин>.github.io/<репозиторий>/crm/`
(GitHub Pages сам отдаёт `index.html`). Старая ссылка на
`crm/Клиенты.dc.html` показывает исходник холста и работать не будет.

Узлы страница не пересоздаёт, а обновляет на месте — поэтому фокус и
каретка в поле ввода не сбрасываются, пока вы печатаете.

`Клиенты.dc.html` → раздел **Настройки** → вставьте адрес Web App и
`API_TOKEN` → **Сохранить подключение**. Оба значения хранятся в
localStorage этого браузера. Остальные строки в настройках показывают
только «задан / не задан» — секреты вводятся в Apps Script.

Кнопка **Проверить подключения** дёргает `action=ping`: Web App сам
проверяет таблицу, GitHub, RouterAI и Telegram и возвращает результат.

Пока адрес Web App не задан, интерфейс работает на демо-данных и ничего
никуда не отправляет — в шапке написано «демо-данные».

Повторный клик по текущему пункту меню — перезагрузка данных из таблицы.

## Как это работает внутри

**Почему POST уходит с `Content-Type: text/plain`.** Apps Script не
отвечает на preflight-запрос `OPTIONS`, поэтому `application/json` в
браузере упёрся бы в CORS. `text/plain` делает запрос «простым» —
preflight не нужен, тело всё равно разбирается как JSON.

**Коммит конфига.** `action=push` сначала сохраняет карточку, затем
собирает конфиг (тот же, что показан в предпросмотре интерфейса), берёт sha
текущего `clients/{id}.json`, кладёт новый через PUT (base64, UTF-8) и
запускает `workflow_dispatch` с `client_id` во входных данных. Если
воркфлоу не объявляет такой input, запуск повторяется без него; если
воркфлоу нет — коммит всё равно засчитан, а в интерфейсе видно, что
прогон не запустился.

**Оплаты.** CRM их только показывает. Статус читается из колонки
«Статус», дата — из «Дата оплаты»; ни то, ни другое CRM не записывает,
даже когда карточка сохраняется целиком. Кнопка «Открыть строку в
таблице» ведёт на ячейку статуса нужной строки
(`…/edit#gid=…&range=F7`), там же дропдаун. То же самое делает кнопка «В
таблицу →» в разделе «Оплаты».

Новым клиентам CRM не проставляет ни дату, ни статус — их ставит Владимир
дропдауном. До этого клиент показывается как «Новый бриф».

Дропдаун из `addDropdown` покрывает 100 строк начиная со второй. Если CRM
завела клиентов дальше 101-й строки — запустите `addDropdown` ещё раз.

**Генерация.** Все обращения к RouterAI идут из Apps Script. Кнопки
интерфейса сначала сохраняют карточку, поэтому модель работает с тем, что
на экране. Результат сразу пишется в таблицу — `style_prompt` в свою
колонку, рубрики в «Рубрики (JSON)», — и возвращается в интерфейс. При 429
и 5xx запрос повторяется трижды с паузой.

## Проверки

```
node crm/tests/run.js
```

Прогоняет разбор значений, работу с таблицей (на мок-таблице), GitHub и
RouterAI (на мок-ответах) и весь интерфейс с подменённым `fetch` — без
Google, ключей и сети.

Собранную страницу можно проверить в браузере: открыть `crm/index.html`
локально — должны отрисоваться демо-данные, а в шапке — «демо-данные».
Если вместо текста видны `{{ переменные }}`, значит открыт холст
`Клиенты.dc.html`, а не собранный `index.html`.
